# Saan Prototype v0.2 设计：设计规范包

状态：设计已与用户确认（2026-11-06），尚未实现。v0.1 的设计见 [2026-11-05-saan-prototype-design.zh-CN.md](2026-11-05-saan-prototype-design.zh-CN.md)。

## 1. 要解决的问题

v0.1 的原型只能用内置的三套主题和一组通用页面样式。团队已有设计系统时（例如一套有令牌、几十个组件和内容规范的内部设计系统），评审原型和最终界面长得不一样，用词也不一样：

- 评审时容易争论“上线后不会是这样”，偏离对规则的讨论；
- 开发拿到原型，不知道每个区块该用哪个组件；
- 原型里出现设计系统禁止的写法，例如“您”、感叹号、只写“确定”的按钮、只写“操作失败”的报错。

v0.2 让用户指定一个**设计规范包**。原型按它的令牌配色，按它的组件清单搭页面、标组件名，按它的内容规则写文案，检查器再核对其中能机械判断的部分。

## 2. 已确认的选择

| 问题 | 选择 | 放弃的方案 |
|---|---|---|
| 设计系统放在哪个技能 | saan-prototype 增加可选输入 | 单独的 design-system 技能（面向前端开发、产出代码，是另一件事，以后再做） |
| 原型里用不用真实组件代码 | 不用。runtime 补几种通用组件外观，页面标上规范里的组件名 | 内联 Vue 和组件库（单文件 1 MB 以上，容易被误当成可上线代码） |
| 规范包从哪来 | 用户提供目录，技能只读 | 技能内置某个公司的设计系统（不能进公开仓库） |
| 没有规范包时 | 行为与 v0.1 完全相同 | 默认启用一套内容规则 |

## 3. 规范包格式

用户提供一个目录，结构如下：

```text
<design>/
  design.json     名称、版本、主题、组件清单、内容规则（机器读）
  guide.md        版面和交互规则的文字说明（Agent 读）
```

`design.json`：

```json
{
  "name": "示例规范",
  "version": "1.0",
  "themes": {
    "light": {"label": "示例浅色", "bg": "#F5F6F8", "surface": "#FFFFFF", "border": "#D5D8DE",
              "text": "#1F2329", "muted": "#5C6370", "accent": "#2F5D9E", "accent_text": "#FFFFFF",
              "danger": "#B42318", "notice": "#8A5A00", "success": "#1A7F37",
              "radius": "4px", "font_size": "14px"}
  },
  "components": {
    "StatusBadge": {"use": "status", "rule": "单据状态统一用它，同时显示颜色、图标和文字"},
    "ActionBar": {"use": "actions", "rule": "不能执行的动作保留，并写明原因"},
    "ChangeConfirm": {"use": "confirm", "rule": "提交、退回、作废前列出每项变化和后果"},
    "Field": {"use": "field", "rule": "查看态显示文字，不用禁用的输入框"},
    "FilterBar": {"use": "filter", "rule": "默认最多 3 个条件，其余收进“更多条件”"},
    "DataTable": {"use": "table"},
    "PeriodPicker": {"rule": "显示每个月的结账状态"}
  },
  "content": {
    "forbid": [
      {"text": "您", "message": "称呼用“你”或省略主语"},
      {"text": "！", "message": "不使用感叹号"},
      {"text": "操作失败", "message": "说明缺什么、在哪里改、找谁处理"}
    ],
    "button_forbid": [{"text": "确定", "message": "写明动作和对象，如“提交审批”"}]
  }
}
```

- **`themes`**：键名和 runtime 现有的主题令牌一致，另加可选的 `success`。每套都要通过对比度检查。设计系统的令牌名不同，由写规范包的人对照一次，不在运行时转换。
- **`components`**：键是设计系统里的组件名。`use` 指向 runtime 的通用组件（第 4 节）；没有 `use` 的组件用基础样式搭建，并在追溯表中注明“外观近似”。`rule` 是一句使用规则，Agent 选组件时读。
- **`content`**：纯文本匹配，不支持正则。`forbid` 匹配文案中的任意位置；`button_forbid` 只在按钮的完整文字等于它时命中，所以“确定”会被拦下，“确定人选”不会。规则写不成固定文字的，放进 `guide.md`。
- **`guide.md`**：长表单一页展开、弹窗只做短任务、每个视图一个主按钮这类规则。检查器不读它。

`references/design-profile.md` 说明这个格式，以及怎样从现有设计系统的文档整理出一个规范包。Agent 可以帮用户起草，但起草的包要标为草稿，由用户确认后再用。

## 4. runtime 补充的通用组件

只补 ToB 评审中反复出现、且和规则表达直接相关的几种。它们只负责外观和行为接近，不是组件库：

| `use` | 写法 | 作用 |
|---|---|---|
| `status` | `<span class="p-status" data-tone="success">已审核</span>` | 颜色、图标和文字同时显示；`tone` 取 neutral、success、notice、danger |
| `actions` | `<button data-action="submit" data-disabled-reason="…">` | 不可用的按钮保留显示，原因直接显示在按钮旁，不只靠悬停 |
| `confirm` | `c.confirm({title, changes, effects, confirm: {text, proposal}}, "action")` | 列出每项“原值 → 新值”和后果，确认后才执行动作 |
| `field` | `<div class="p-field read" data-changed-from="…">` | 查看态显示文字；编辑时标出修改前的值 |
| `filter` | `<details class="p-filter">` | 常用条件外露，其余收起，并显示已生效的隐藏条件数 |
| `table` | `.p-table` 加 `.p-cell-sub` | 一格内两行信息（主信息和说明） |

例：room-booking 中管理员 M 取消他人预约，PRD 的流程是“取消 → 填写原因 → 确认”（FR-M01—FR-M04）。v0.1 的原型用普通对话框；指定规范包后，同一个对话框改用 `confirm` 的样式：原因输入框之下列出变化“状态：有效 → 已取消”和后果“释放该时段的占用”。预约人能否看到取消原因还没定（Q-08），后果里放一个待定块，不写成确定的结果。确认按钮文字仍是建议「确认取消」。

`confirm` 和 `actions` 的反馈仍然来自规则函数。规范包只改变怎么呈现，不增加业务步骤：来源没有要求确认的操作，加确认框本身也要标为建议（`data-proposal`），与 v0.1 对“为了跳转而加的入口”的处理一致。

## 5. 组件名标注

- 页面元素写 `data-component="StatusBadge"`。名称必须在规范包的 `components` 里。
- 评审栏增加“组件名”开关，默认关闭。打开后，每个标了组件的区块显示组件名角标，和现有的建议、待确认、规则角标分开。
- `trace.md` 增加“页面—组件”表：每个页面用了哪些组件，哪些是外观近似。开发据此对照组件库。

没有规范包时，不显示开关，`data-component` 也不需要写。

## 6. 检查

指定规范包时，`check.py` 增加 D 类检查；没有规范包时一条都不运行，原有检查不变。

| 编号 | 级别 | 检查内容 |
|---|---|---|
| D1 | 必须修改 | `data-component` 的名称不在规范包中 |
| D2 | 必须修改 | 页面或规则文案命中 `content.forbid` 或 `button_forbid` |
| D2 | 业务发现 | 命中的是来源已确认的文案（`confirmed_text`）：报告给用户，不能为了通过而改 |
| D3 | 提示 | 同一页面的静态代码里出现不止一个 `.p-btn.primary` |
| D4 | 必须修改 | 页面代码里写死了色值（`#xxx`、`rgb(`），而不是用主题令牌 |
| B2 | 必须修改 | 规范包的主题也做对比度检查，缺少令牌也报在这里；带 `success` 时，它对 `surface` 不低于 4.5:1 |
| M1 | 必须修改 | `design.json` 缺失、无法解析，或结构不对（没有主题、`use` 不是第 4 节的取值） |

D2 和 D3 是对静态代码的文本扫描，会去掉注释，但仍可能漏报，也可能把同一页面里互斥分支的按钮算两次，所以 D3 只作提示。检查器仍然不判断交互好坏，也看不出 `guide.md` 里的规则有没有被遵守。

## 7. 工作流程的变化

1. **读材料时同时读规范包。** 用户提到设计系统、规范或组件库，或者给了目录时使用它。没有提到时不单独询问，用内置主题，并在交付说明里写一句“可以指定设计规范包”。
2. **范围清单里写明使用的规范包**，例如“4 个页面、2 个角色、9 个场景，按《示例规范 1.0》”。
3. **复制规范包。** 和 `source.md` 一样，把 `design.json` 和 `guide.md` 复制到 `prototype/design/`，manifest 写 `"design": "design/design.json"`，让目录移动后仍能打包。
4. **搭页面时先按 `components` 选组件，再按 `guide.md` 排版。** 规范和来源冲突时（例如规范要求确认框，来源没写），以来源为准，冲突写进 `trace.md`。
5. **交付时多报告两项**：用到的组件清单，以及 D2 业务发现。

## 8. 验证

上架前完成：

1. **回归。** 不带规范包时，现有示例的检查结果不变，现有 20 个单元测试和 `--selftest` 继续通过。runtime 有改动，所以站点演示 `page/prototype/example.html` 要重新打包，站点检查会比对它和全新打包的结果。四个已记录的验证原型用新 runtime 重新打包，逐个场景渲染没有脚本错误。
2. **自测。** `--selftest` 为 D1—D4 各加一个改坏的样例。
3. **单元测试。** 规范包加载、主题合并、`design/` 复制后的相对路径、`confirm` 的确认与取消。
4. **全新上下文运行。** 用 room-booking 的 PRD 加一个虚构的规范包，评审标准在生成前写定。重点看：
   - 是否只用了清单里的组件名，组件名标注是否和页面一致；
   - 是否没有因为规范而增加来源以外的步骤；
   - 和来源冲突的规范要求是否写进了 `trace.md`；
   - D2 的业务发现是否如实报告，而不是改掉已确认的文案。
5. **私有试用（不进仓库）。** 用户在自己的目录里，用真实的设计系统跑一次，只把发现的问题记成虚构的复现样例。

## 9. 已确认的细节

1. 组件名角标只显示规范里的名字。
2. v0.2 不支持覆盖字体和控件高度，只覆盖颜色、圆角和字号。
3. 规范包可以带多套主题（包括深色），评审栏都能切换；不强制。
4. 仓库里放一个虚构的“示例规范”，只用于示例和测试。
5. 版本号 `0.2.0`，标签 `saan-prototype/v0.2.0`。

## 10. 局限

- 原型只是外观接近设计系统，不保证像素一致，也不代表组件库的真实行为。
- 能机械检查的只有组件名、禁用文字、主按钮数量和色值；`guide.md` 里的规则靠 Agent 遵守、评审时人工看。
- 规范包的质量决定结果。从文档整理出来的规范包，可能漏掉规则或理解错。
