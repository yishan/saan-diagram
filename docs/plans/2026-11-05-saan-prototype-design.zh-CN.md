# Saan Prototype 设计

状态：设计已与用户逐节确认，尚未实现。按 [CONTRIBUTING](../../CONTRIBUTING.md)，实现并验证之前不创建 `skills/saan-prototype/`，以免被识别为可安装技能。

## 1. 定位与已确认的选择

`saan-prototype` 把需求变成**评审用的可交互原型**：一个单独的 HTML 文件，浏览器直接打开，不需要安装或构建。原型用来对齐交互、状态和规则，不承诺可以直接上线，也不替代视觉设计稿。

| 问题 | 选择 | 放弃的方案 |
|---|---|---|
| 给谁用 | 评审演示：原生 HTML/CSS/JS 单文件 | 前端工程起点（依赖重、难验证）；两者都做（首版周期过长） |
| 未定内容怎么呈现 | 可切换的标注层，默认打开，关闭后是干净的演示版 | 始终显示（演示时杂乱）；不标注另附清单（容易被误当定稿） |
| 内置资产 | 多套主题，每套只是一个 token 文件；外加少量页面范式 | 单一风格；不内置风格（每次风格都不同） |
| 交互深度 | 示例数据，加上已确认规则的 JS 实现，评审栏可切换角色和场景 | 点击走查（试不出边界情况）；完整前端逻辑（容易被误当实现） |
| 生成方式 | 内置运行时，Agent 写页面、数据和规则，由脚本打包 | Spec 渲染器（复杂交互难表达）；Agent 自由手写（每次写法都不同） |

## 2. 输入、输出与包结构

**输入。** 首选 `saan-prd-writing` 那样的需求规格，包括功能清单、界面设计表、功能约束、验收场景和待确认事项。没有 PRD 时，也接受需求描述或截图，但要先列出所做的假设。`saan-prd-writing` 是可选的同级技能，不是前置条件。

**输出**（放在用户的工作目录）：

- `prototype.html`：内联了运行时、主题和页面的单个文件。
- `prototype/`：页面、示例数据、规则和场景的源码，修改后可以重新打包。
- `trace.md`：每个页面、标注和场景对应的来源编号，以及没有画进原型的内容和原因。

**包结构：**

```text
skills/saan-prototype/
  SKILL.md
  runtime/      标注层、角色/场景面板、主题切换、组件样式
  themes/       每套主题一个 token 文件
  patterns/     页面范式参考：列表、表单、详情、时间轴/日历、确认弹窗、空/错状态
  scripts/      build.py 内联打包；check.py 一致性检查
  references/   标注规范、场景写法、来源处理
```

运行时和主题都放在包内，不使用跨技能的共享路径。打包和检查只用 Python 标准库。

**不做：** 前端工程、真实接口、数据持久化、移动端设备外框。

## 3. 运行时

运行时提供每个原型都要用的公共部分，Agent 不重写。

- **评审栏。** 固定在页面顶部，包含角色切换、场景选择和标注开关。关闭标注后，评审栏收成一个小按钮。
- **标注 API。** 页面里用 HTML 属性声明：
  - `data-proposal="<编号>"`：〔建议〕文案。加角标，悬停时显示"建议文案，未确认"和来源编号。
  - `data-open="<Q 编号>"`：待确认事项。挂上编号气泡，点开后显示问题原文和影响范围。待确认的位置放一个占位块，写明"此处待 Q-xx 决定"，不编造确定的界面。
  - `data-rule="<FR 编号>"`：已确认的规则，只在标注层显示编号。
- **场景。** `scenarios.js` 中每个场景包含名称、对应的验收场景编号、初始数据、当前角色和当前时间。当前时间也是场景的一部分，因为"已开始"这类规则要靠时间触发。切换场景会重置数据。
- **规则。** `rules.js` 用纯函数写来源中**已确认**的规则，页面调用它们得出反馈。待确认的规则不写成逻辑，界面上显示成 `data-open` 占位。
- **主题。** `themes/*.json` 只放 token（颜色、圆角、字号、间距），组件样式全部引用 token，评审栏可以切换。首版 3 套：中性灰（与 Saan 图示一致）、品牌蓝、暗色。

例：在 room-booking 中选场景「AC-08 并发提交」，再以员工乙的身份提交同一时段，页面出现冲突反馈。反馈文案带〔建议〕角标，并挂着 Q-12。

## 4. 工作流程

1. **读材料，列页面清单。** 从功能清单和界面设计表整理出页面、入口、角色和状态，并摘出〔建议〕文案、待确认事项和验收场景。材料不足时只问一个关键问题；用户要求直接出稿时，把假设写进 `trace.md`。
2. **确认范围。** 给出简短的页面和场景清单，例如"4 个页面、2 个角色、9 个场景"。用户已经指定范围时不再询问。
3. **选范式和主题。** 页面只从 `patterns/` 中挑写法。主题按用户指定选取，没有指定时用默认主题。
4. **写文件。** 先写 `rules.js` 和 `scenarios.js`，再写页面。页面的反馈由规则函数决定，这样界面和规则不会各说各的。
5. **打包并检查。** 运行 `build.py` 打包，再运行 `check.py`。
6. **交付。** 说明打开方式、场景列表、没有画进原型的内容，以及待确认事项的数量。

## 5. 检查

`check.py` 延续另外两个图示技能的区分：排版类问题直接改到通过；业务发现只报告，不准为了通过而改。

| 类别 | 检查内容 |
|---|---|
| 追溯 | 每个标注编号都能在来源中找到；来源中的每个待确认事项，要么出现在原型里，要么在 `trace.md` 中写明不涉及 |
| 场景 | 每个场景都引用存在的验收编号；没有覆盖到的验收场景单独列出 |
| 一致性 | 原型中的角色和状态集合与来源一致，不新增状态 |
| 文案 | 来源中已确认的文案原样出现；其余文案都必须标为建议 |
| 打包 | 单个文件、没有外部网络请求、各主题对比度达标 |

检查只核对编号和文本，不能判断交互是否好用。

## 6. 验证

上架前完成：

1. **脚本自测。** `check.py --selftest` 用故意改坏的样例证明每条检查都会触发。`build.py` 另配单元测试，两者都接入 CI。
2. **room-booking 第 5 步。** 把 [第 2 步产出的 PRD](../../tests/e2e/room-booking/results/2026-11-05/02-prd/prd.md) 交给隔离环境中全新上下文的执行者，评审标准在生成前写定。重点看这几项：
   - 已确认的文案和规则是否原样保留；
   - 待确认事项是否画成占位；
   - 场景是否覆盖 AC-01—AC-24 中能在界面上演示的部分；
   - 是否加了说明书中没有的步骤。端到端案例的图示步骤犯过这个错。
3. **无 PRD 案例。** 只给需求描述，检查假设清单是否完整、有没有冒充已确认的内容。
4. **人工打开。** 用本机 Chrome 实际操作一遍并截图存档。这一步验证能用，不代表好用。

## 7. 局限

- 原型是评审工具，示例数据为虚构，规则只覆盖已确认的部分。
- 检查不评价交互质量，也没有真实用户可用性测试。
- 多套主题只保证对比度，不保证品牌合规。
