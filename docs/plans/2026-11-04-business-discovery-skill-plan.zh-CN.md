# Saan Discovery 业务调研技能规划

## 1. 定位与已确认范围

正式名称：`saan-discovery`，展示名称：Saan Discovery，中文说明：业务调研助手。

帮助产品经理、业务分析师和实施顾问结合已有产品逻辑，准备客户访谈、整理调研记录、识别关键缺口，并形成有依据的产品适配判断。

用户已确认主要使用方式为“调研助手”：由用户开展客户访谈，AI 准备提纲、整理记录并追问缺口。AI 不默认直接主持客户访谈。

核心目标是回答：**为判断已有产品怎样契合客户业务，当前还缺哪些信息，应当向谁获取，答案会影响什么决定？**

本文件保留最初面向企业的设计研究。技能已在本地实现，访谈方法纳入内部参考文件。v0.2.0 按后续要求增加 ToC、ToB/G 与混合场景分流，并默认交互确认范围、逐专题补充；当前行为以[技能入口](../../skills/saan-discovery/SKILL.md)为准。模拟运行与实际检查分别见 [v0.1.0 验证记录](../saan-discovery/validation.zh-CN.md)和 [v0.2.0 验证记录](../saan-discovery/validation-v0.2.zh-CN.md)；真实客户调研效果尚未验证。

## 3. 结合已有产品逻辑的方法

### 3.1 先建立产品基线

读取用户提供的产品说明、现有流程、操作手册、需求文档、代码或可访问系统。只读取本次业务范围相关材料。

至少提取：

- 产品处理的业务对象及其关系，例如合同、付款申请、项目、组织。
- 对象的生命周期、关键状态和生效条件。
- 角色、数据范围与可执行动作。
- 已有业务规则、审批机制和可配置维度。
- 关键字段、数据来源、上下游系统和输出。
- 已知限制、版本范围与材料证据。

材料不同，证明范围也不同：产品文档说明设计口径；代码说明实现行为；部署配置说明环境设置；实际操作记录说明被观察到的业务路径。分别记录，不能相互替代。

产品资料缺失时，先开展客户业务理解，并把产品适配结论标记为待核实。不要让资料缺失阻断全部调研，也不要用行业惯例补写产品能力。

### 3.2 双向比较

从产品出发，识别实施或适配必须知道的客户条件。例如：产品按组织匹配审批人，就需要知道客户的组织口径、岗位关系和跨组织处理方式。

从客户业务出发，识别产品材料没有覆盖的任务、线下协调和特殊分支。例如：客户在合同变更后仍沿用原付款计划，这可能涉及产品原有状态与数据关系之外的问题。

先记录客户现状，再讨论目标做法和产品映射。产品能力用于选择调研重点，不能被当作客户理应遵循的答案。

### 3.3 将产品依赖转成必问信息

| 产品基线中发现的依赖 | 客户侧必须核实的信息 | 可能影响的判断 |
|---|---|---|
| 审批由金额、组织或类型驱动 | 金额口径、边界是否包含等号、组织口径、例外授权 | 已有配置能否表达客户规则 |
| 业务对象有固定状态流 | 客户何时认为业务生效；退回、撤回、变更后如何处理 | 状态映射和是否需要调整行为 |
| 数据来自其他系统 | 哪个系统维护权威数据、谁负责、何时更新、失败如何处理 | 集成范围与人工补偿方式 |
| 系统按角色限制数据和动作 | 经办、复核、审批、查询分别能处理什么范围 | 权限配置与组织职责匹配 |
| 管理报表依赖业务填报 | 谁录入、何时录入、口径如何统一、能否回溯来源 | 数据完整性与指标可实现性 |

每个问题应能回溯到业务判断或信息缺口。没有关联的问题，可作为条件问题保留，不进入本轮必问清单。

## 4. 调研覆盖框架

“必备信息”表示该维度必须有明确记录。记录可以是已知、有待确认、存在冲突，或附理由的不适用；并不表示每轮都要重复提问。

| 维度 | 必须能够说明的内容 | 值得追问的缺口 |
|---|---|---|
| 目标与范围 | 具体岗位、所做任务、为什么现在处理、不做后果、涉及组织与业务范围 | 需求提出人、决策人、实际使用人、数据提供方是否不同 |
| 业务流程 | 触发条件、输入、参与者、实际步骤、交接、输出、结束条件 | 最近一次怎样完成；哪些步骤发生在系统外 |
| 审批流程 | 需审批的对象、决策权、路由条件、审批结果及其业务后果 | 审批通过是否立即生效；退回或修改后从哪里继续 |
| 业务对象与规则 | 单据/对象关系、关键字段、状态、计算或判断依据 | 同名字段是否同义；条件边界与例外由谁定义 |
| 业务摩擦 | 发生在哪一步、影响谁、发生频率、实际成本、当前补救 | 操作时间与等待时间分别多少；是否存在返工、重复录入或责任空档 |
| 当前做法与证据 | 使用的系统、表格、纸张、群消息和记录；制度规定与实际做法 | 制度写法、管理者陈述与一线操作是否一致 |
| 期待与验收 | 期望改变的业务结果、保留条件、优先级、评价方式与确认人 | “更快、灵活、方便”分别意味着什么；基线和目标是否有来源 |
| 产品适配 | 客户规则与产品能力的对应关系、差异、依据和待核实内容 | 是参数配置、流程调整、集成、能力缺口，还是目前证据不足 |

以下内容按场景触发，不默认变成长问卷：

- 涉及多组织或多岗位：数据隔离、跨组织协作、岗位兼任、职责分离。
- 涉及外部系统：主数据归属、关联标识、同步时点、失败补偿和对账责任。
- 涉及历史替换：数据迁移范围、旧业务续办、切换时点与历史查询。
- 涉及批量或时限：业务量、峰值、响应时限、离线或移动使用条件。
- 涉及推广落地：配置维护人、业务负责人、培训、试点范围与持续使用者。

## 5. 业务流程与审批流程分开建模

业务流程描述工作怎样完成。审批流程描述谁在什么条件下作出授权、复核或批准。审批通常只是业务流程中的一段。

例如“申请 → 审批 → 执行 → 核对 → 归档”中，审批通过并不自动证明执行完成，也不自动证明数据核对完成。

业务流程记录字段：

`步骤 → 触发条件 → 角色 → 输入 → 动作 → 输出/状态变化 → 下一接收方 → 异常 → 来源`

审批规则记录字段：

`审批对象 → 触发条件 → 路由条件 → 审批人确定方式 → 审批动作 → 结果 → 业务后果 → 例外 → 来源`

当现有材料触发相关分支时，继续检查：

- 审批对象是整单还是明细；明细能否部分通过。
- 条件涉及金额、类型、项目或组织时，各维度如何组合，边界值如何归属。
- 串行、并行、会签或或签的完成条件。
- 审批人缺席、岗位空缺、兼任或本人发起时，实际如何处理。
- 退回、驳回、撤回、转交、加签、超时等动作的区别和适用条件。
- 退回重提是否保留原审批结果；关键字段修改后是否重新审批。
- 审批通过后何时生效；后续变更、作废如何影响已执行业务。
- 线下特批、紧急办理和事后补办是否存在；依据、授权人和留痕方式是什么。

上述均为调研方向，不预设客户存在这些规则，也不预设产品已经实现这些能力。

## 6. 从 grill-me 改造的追问机制

### 6.1 建立缺口清单

每个问题包含：

`编号、关联判断、已知材料、未知信息、适合回答的岗位、前置问题、影响、期望证据、状态`

状态可使用：未问、已回答待核实、证据已核对、存在冲突、待其他岗位补充、明确延期、不适用。无需人为计算总体置信分数。

### 6.2 选择下一轮问题

1. 从已有资料和记录中提取答案，避免重复询问。
2. 找到会影响业务范围、职责、审批权、数据有效性、产品适配或验收的缺口。
3. 优先处理会阻塞其他问题的前提；并行问题可以在同一轮提出。
4. 根据本次访谈岗位和可用时间裁剪问题。
5. 用户补充答案后，更新相关事实、冲突和后续问题。

内部补问默认每轮聚焦 3–5 个相关缺口，可随用户要求调整。交付给客户的访谈提纲可以完整列出，但应区分本次必问和条件追问。

每一问只处理一个主旨。问题中的背景只保留回答所必需的信息。

### 6.3 区分事实问题与决策问题

客户事实问题使用中性问法：“最近一次退回后，申请人改了哪些内容？再次提交从哪个环节开始？”

需要用户选择调研范围或验证顺序时，可以提供建议和理由：“建议先核实审批对象，因为它会影响后面的路由和权限问题。”

不要在事实问题中预填“推荐审批规则”，也不要把“是”设计成默认认同产品方案。

### 6.4 从抽象描述深入到证据

建议顺序：实际经历 → 流程定位 → 原因和代价 → 条件与异常 → 复述确认。

遇到“审批很慢”，先问最近一次卡在哪一环，再区分材料不齐、排队等待、重复审核、职责不清或系统操作成本。找到原因后，才讨论改善方向。

遇到用户不知道的客户规则，记录应补问的岗位和所需材料；岗位也不明确时，把“定位规则负责人”列为待办。不持续要求用户猜答案。

### 6.5 收敛条件

根据阶段判断完成程度：

- 访谈准备完成：目标、对象和本次必问问题清楚，已有资料中的答案已复用。
- 单轮整理完成：新增材料已归入流程、规则、摩擦和期望，来源与冲突可追溯。
- 可进入方案评估：关键业务路径、重要分支、规则责任人和验收方向足够明确；高影响未知已列明其阻塞范围和验证动作。
- 仍需补充调研：关键规则或岗位缺失，影响产品适配判断；只输出有依据的阶段结论。

达到时间边界时也应交付阶段结果。结束本轮不等于所有规则已确认。无需为了显得充分而继续追加低价值问题。

## 7. 证据、冲突与适配判断

每条重要陈述同时记录两个维度：

- 内容类别：当前做法、制度要求、目标期待、产品设计、产品实现、分析建议。
- 证据情况：现场观察、文件/记录佐证、受访者陈述、分析假设、存在冲突、待确认。

来源至少能够定位到材料、页码/段落或时间点，以及相关日期、岗位和适用范围。原话与转述要区分。

不同岗位的说法发生冲突时，保留双方陈述并检查组织、业务类型、金额条件和时间范围。不能简单取多数意见，也不能把管理者口径直接作为一线实际操作事实。

客户说“需要”，表示需求表达。它不自动证明该规则已获授权、产品已支持、客户愿意为调整承担成本或目标已经验收。

适配判断采用以下分类，并允许一项需求组合多种实现路径：

| 分类 | 需要的依据 |
|---|---|
| 已有能力覆盖 | 客户条件与产品行为相匹配，证据注明版本和验证范围 |
| 可配置适配 | 已核实可配置的参数、维度、边界和限制 |
| 业务做法调整 | 明确改变谁的工作及其代价，客户责任人是否接受另记 |
| 系统集成 | 两侧能力、权威数据、同步规则和责任边界已明确 |
| 产品能力缺口 | 明确客户必要行为与已核实产品行为之间的差异 |
| 待核实 | 客户规则、产品能力或两者关系尚无足够证据 |

“产品能力缺口”不等于承诺定制。开发可行性、成本、排期和立项决定在后续评估中处理。

## 8. 三个使用阶段与交付物

| 阶段 | 典型输入 | 主要输出 |
|---|---|---|
| 访谈前准备 | 产品材料、客户背景、本次对象和目标 | 产品基线摘要、按岗位组织的访谈提纲、要查看的业务证据、关键假设 |
| 访谈后整理 | 纪要、录音转写、单据、表格和页面记录 | 现状流程、审批规则、摩擦、期待、证据与冲突记录 |
| 查漏与补访 | 既有调研文档、新增信息、待评估方案 | 优先补问清单、适合回答的岗位、定向补充问卷、适配判断更新 |

建议每个客户或项目维护一份持续更新的调研底稿。小任务允许合并在单个 Markdown 文件中，不机械拆分文件。

调研底稿的最小结构：

1. 调研目标、范围、参与岗位、产品版本与材料范围。
2. 业务对象、术语和流程；审批流程单列。
3. 当前摩擦及影响证据。
4. 目标期待、优先级和验收方向。
5. 客户规则与产品能力对应表。
6. 信息缺口、冲突、负责人或候选岗位、下一步验证动作。

客户用提纲只保留回答所需的背景、问题和可提供材料。内部的产品能力判断、问题优先级理由和假设放在调研底稿中。

流程复杂时，先用步骤表或简图表达关系。`saan-diagram`、`saan-mermaid` 可作为可选图示工具；核心调研流程不依赖安装这些技能。

## 9. 示例：付款申请调研

以下完全为虚拟演示材料，不代表任何现有产品能力或客户规则。

假定产品资料已说明：付款申请关联一份合同；审批可按金额和组织设置条件；驳回后允许修改并重提。资料没有说明 OA 集成和修改后的审批继承规则。

客户初步陈述：“付款审批慢，线下沟通很多，希望能灵活一点。”

根据产品依赖和客户陈述，准备以下问题，而不是直接建议增加审批功能：

| 顺序 | 中性问题 | 优先询问的岗位 | 获取的信息如何使用 |
|---|---|---|---|
| 1 | 请选最近一笔已经处理完的付款申请，按实际顺序讲述从发起到付款完成的经过。 | 经办人 | 识别实际流程、系统外步骤和审批结束后的执行环节 |
| 2 | 这笔业务在哪一步等待最久？ | 经办人、相关审批岗位 | 定位摩擦；再追问等待原因和可用时间记录 |
| 3 | 实际申请与合同之间如何对应？是否存在一笔申请涉及多份合同的实例？ | 经办人、财务 | 核实业务对象关系，检验产品“一份合同”的适配范围 |
| 4 | 哪份现行制度或实际规则决定审批人？ | 业务负责人 | 获得规则来源；随后分别追问金额口径、组织口径和例外 |
| 5 | 最近一次退回重提时，修改后的申请从哪个环节继续？ | 经办人、审批管理员 | 核实重提行为；产品相同行为仍须另行查证 |
| 6 | 你们希望优先改变哪一项业务结果？ | 业务负责人 | 将“灵活”落到具体结果；基线、目标和确认人后续分别核实 |

如果客户补充“所有审批都走 OA”，则产生新的资料核实和补问任务：OA 实际承载哪些动作、业务系统何时更新状态、谁维护规则、能否获得记录。没有资料证明集成能力时，适配结论保持待核实。

如果用户不了解 OA 规则，补问清单应指向 OA 管理员或规则负责人。若一线和管理员说法不同，保留冲突并寻找具体单据验证。

## 10. 建议的技能结构

本地实现采用以下结构。技能入口、引用文件和独立安装已检查；运行时不依赖本设计文档。

```text
skills/saan-discovery/
  SKILL.md
  references/
    product-fit.md
    process-and-approval.md
    user-interview.md
    deliverables.md
```

- `SKILL.md`：使用边界、三个阶段、缺口驱动流程、证据规则、收敛条件和参考文件路由。
- `product-fit.md`：读取产品基线、客户条件映射、差异分类和判断限制。
- `process-and-approval.md`：业务流程与审批流程字段，以及按条件触发的异常检查。
- `user-interview.md`：中性提问、依赖排序、定向补问与典型追问示例。
- `deliverables.md`：调研底稿、岗位提纲、缺口表和适配表的精简模板。

最终参考文件数量按内容长度调整；无需为了目录完整而保留空文件。首版以文本流程为主，暂不需要运行脚本。

按当前仓库惯例，技能入口使用英文；输出跟随用户指定语言，未指定时沿用请求语言。用户指南在技能实现后提供中英文版本。

建议的描述草案：

> Prepare customer business interviews, synthesize field notes, and identify decision-critical information gaps using existing product logic. Use for enterprise business discovery, workflow and approval elicitation, and product-fit assessment before solution design or PRD writing.

与其他技能的职责连接：本技能形成调研底稿和待确认清单；图示技能表达流程；未来的 PRD 技能把已确认内容转成需求、规则和验收条目。调研结论不自动变成研发承诺。

## 11. 首版验证计划

以下是设计时的验证目标。已执行的模拟场景、观察到的问题及修正记录见 [验证记录](../saan-discovery/validation.zh-CN.md)，不将模拟通过视为真实客户业务验收。

| 用例 | 通过标准 |
|---|---|
| 产品材料已经回答某项能力 | 引用已有材料，不再把同一事实问给用户；客户规则仍单独核实 |
| 只有“审批慢、想灵活”的表述 | 先索取具体经历并定位流程步骤，不直接提出新功能 |
| 审批通过后还有执行与核对 | 分别记录审批状态和业务完成状态 |
| 用户不知道客户规则 | 输出合适岗位和定向补问，未知保持未知 |
| 不同岗位描述冲突 | 保留来源与适用范围，输出验证动作，不自行裁决 |
| 产品材料缺失 | 继续业务调研，适配结论保持待核实 |
| 已有产品不覆盖客户必要行为 | 清楚标注差异，不诱导客户迎合产品，也不承诺定制 |
| 单一访谈提到高影响异常 | 标注证据范围并核实规则，不因出现次数少而丢弃 |
| 调研时间耗尽或用户要求阶段交付 | 交付已知结果与未决项，说明哪些判断仍受影响 |
| 补充新纪要后继续调研 | 更新已有记录与问题状态，不重新询问已解决问题 |

评审重点：问题是否来自实际缺口；能否改善业务判断；是否保留证据与未知；是否避免诱导；是否控制访谈负担。
