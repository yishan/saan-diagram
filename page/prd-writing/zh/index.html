Saan PRD Writing

v1.0.1

把零散的需求和原型整理成需求文档，让团队能逐项讨论，也让开发和验收有据可查。

把需求说明、评审意见、现有文档或可读取的原型交给它。它会先理清范围，再展开每个功能：谁来用、需要什么条件、操作后改变什么、失败时怎么处理。只改一个功能时，就围绕这次改动写，不必重写整份文档。

适合用在
新项目需求、功能改动与现有文档修订
得到什么
需求文档、验收场景和待确认事项
使用准备
准备需求材料；技能内附中英文模板和示例

先说明整体，再展开功能

完整需求规格说明书

  1. 引言：范围、读者、术语与来源
  2. 项目概况：背景、问题与目标
  3. 系统概述：边界、流程与功能清单
  4. 功能需求：模块与功能详情
  5. 非功能需求：质量要求与验证条件
  6. 总体设计约束：已确认的外部限制

每个功能按同一逻辑展开

  1. 业务描述：角色、场景与业务结果
  2. 界面设计：入口、区域与交互
  3. 业务字段：类型、格式、必填与用途
  4. 功能约束：条件、处理、状态与反馈

只写局部改动时，保留相关章节，并注明沿用哪一版需求。确有补充内容时再使用「其他」一节。

把一句要求写到可以验收

虚构示例 · 采购申请批量归档

“自己创建且已完成的申请可以批量归档。选中任意不符合条件的记录时，整批中止。”
  1. 触发：采购专员选中申请，发起批量归档。
  2. 校验：全部选中申请均由本人创建，且状态为「已完成」。
  3. 结果：任意一条不符合条件时，整批中止，所有记录保持原状。
  4. 验收：选中一条他人创建的申请，检查整批记录均未改变。

如果处理到一半发生系统错误，已处理的记录是否要恢复，仍需确认。上面的要求只说明了不符合归档条件时怎么办。

哪些已经确定，哪些还要讨论

  • 每条规则只完整写一次，界面说明、字段表和验收场景引用同一个编号，避免改动后各处说法不一致。
  • 单据处于什么状态、归在哪个列表、页面显示什么、谁能操作，分别说明。
  • 来源相互冲突时，保留双方依据及需要作出的决定。
  • 模板不预设性能数值、安全等级、技术架构或服务承诺。
  • 建议使用的文案和尚未决定的规则会明确标出。验收场景只依据已经确认的要求。

资源适用情况包含内容
完整需求文档 · 中英文新项目或完整评审六章正文、版本与修订记录、验收场景和待确认事项
局部变更 · 中英文已有项目中的一个需求改动范围、功能详情、对现有需求的影响与验收
采购申请批量归档参考规则写到多细虚构需求、具体规则、状态变化和待确认事项的写法

独立试写另用「会议室预约与改期」需求，检查相邻时段、并发冲突、改期失败保留原预约，以及未决规则的处理。验证材料保留在仓库中。

原型需要当前工具能读取，例如已导出的页面或文件。技能不自带读取 Axure .rp 文件的通用工具；需要 Word 或 PDF 版本时，可另用文档工具排版。
