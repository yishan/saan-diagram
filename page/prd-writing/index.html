Saan PRD Writing

Turn requirements and prototypes into reviewable specifications: who does what, under which conditions, and how the data changes.

From context to functional detail

Complete requirements specification

  1. Introduction: scope, readers, terms, and sources
  2. Project overview: background, problem, and objectives
  3. System overview: boundaries, flows, and function inventory
  4. Functional requirements: modules and individual functions
  5. Nonfunctional requirements: quality targets and verification
  6. Design constraints: confirmed external limits

A consistent structure for each function

  1. Business description: roles, context, and outcomes
  2. Interface design: entry points, regions, and interactions
  3. Business fields: types, formats, requiredness, and use
  4. Functional constraints: conditions, processing, states, and feedback

For a scoped change, keep relevant content and reference the project baseline. Add other information only when needed.

Turn a requirement into observable behavior

Fictional example · Bulk archiving purchase requests

“Purchasing specialists can bulk archive completed requests they created. If any selected record is ineligible, reject the entire batch.”
  1. Trigger: a purchasing specialist selects requests and starts bulk archiving.
  2. Validation: every selected request was created by the current user and is completed.
  3. Result: if any request is ineligible, reject the entire batch and leave all records unchanged.
  4. Acceptance: include a request created by another user and verify that no selected record changes.

Rollback after a processing error remains a separate decision. The validation-failure rule does not define that outcome.

Keep requirements, proposals, and unknowns distinct

  • Define each rule once. Reference its identifier in interface descriptions, fields, and acceptance scenarios.
  • Distinguish business states, list groups, display labels, and permitted actions.
  • When sources conflict, retain both references and identify the decision needed.
  • Templates do not supply default performance values, security levels, architectures, or service commitments.
  • Label proposed wording and unresolved rules. Derive acceptance scenarios from confirmed requirements.
