Saan Prototype

v0.1.0

Turn a requirements specification into an interactive prototype that reviewers can click through before anything is built.

Give it a specification with numbered rules, acceptance scenarios, and open questions. It writes one offline HTML file: switch roles and scenarios, try the success and failure paths, and see which wording is still a proposal and which decisions are still open.

Use for
Review sessions on pages, roles, states, and rules
Outputs
One HTML file, editable sources, and a trace table back to the specification
To get started
A PRD works best; a short description also works, with assumptions listed

Try the bundled example

A fictional device-borrowing specification with two roles and three scenarios (in Chinese). Use the bar at the top to switch scenario, role, theme, and annotations.

Sample data is fictional. Open the example on its own.

From specification to review file

What it reads

  1. Functions and pages: what each screen offers and where it is reached from
  2. Roles: who can see and do what
  3. Functional constraints: conditions, state changes, and failure feedback
  4. Acceptance scenarios: the cases reviewers should be able to try
  5. Open questions and proposed wording, kept as they are

What it writes

  1. prototype.html: one file with the runtime, theme, and pages inlined
  2. rules.js: one small function per confirmed rule
  3. scenarios.json: each scenario's acceptance IDs, role, current time, and data
  4. pages/*.js: the pages, built from list, detail, form, dialog, state, and timeline patterns
  5. trace.md: pages and scenarios mapped to source IDs, and which open questions are left out and why

The scope comes first, for example “4 pages, 2 roles, 9 scenarios”, so you can cut it down before anything is built.

Turn a rule into something reviewers can click

From the validation run · Room-booking conflicts

“A booking occupies [start, end). Two active bookings for the same room conflict if their intervals overlap. Back-to-back bookings, such as 09:00–10:00 and 10:00–11:00, do not conflict.”
  1. Rule: FR-C04 becomes one function. The booking dialog calls it and shows its result.
  2. Scenario: “B books around A's weekly meeting and in another room” covers AC-02, AC-03, and AC-04, with A's 09:00–10:00 meeting already in place.
  3. Try it: 10:00–11:00 in the same room succeeds, 09:30–10:30 is rejected and A's booking stays unchanged, and 09:00–10:00 in another room succeeds.
  4. Open: the conflict message is not final (Q-12), so the wording carries a proposal badge and the question opens from it.

Concurrent submissions (FR-C05) cannot be shown by clicking. The trace table says the prototype shows only the visible half.

What reviewers can do

  • Pick a scenario. Each one names its acceptance IDs and sets its own data and current time, because rules such as “already started” depend on time.
  • Switch roles to compare what each person can see and do on the same page.
  • Keep annotations on to see proposed wording, open questions shown as placeholders, and the rule ID behind each control. Turn them off for a clean demo.
  • Choose a neutral, blue, or dark theme. Each theme passes a contrast check.

Only what the specification confirms

  • Confirmed rules become small functions; the pages take their feedback from them.
  • An open question is never implemented as a guess. It appears as a placeholder, or the trace table gives a reason for leaving it out.
  • No pages, steps, or states beyond the specification. Anything added only to move between pages is marked as a proposal.
  • The checker traces every annotation and scenario to an ID in the source, rejects new states and external requests, and lists acceptance scenarios that no scenario covers.

Two cases were each run twice in fresh contexts against criteria written before generation: the room-booking PRD (24 acceptance scenarios) and a one-paragraph description with three rules and no PRD. All four runs met the criteria. Review found runtime and documentation gaps, which were fixed between rounds.

The checker matches IDs and text. It does not judge interaction quality, and the prototype has not been tested with real users.

When to use this skill or another one

Use it before a review, when people need to click through pages, roles, and states rather than read about them. To write the requirements themselves, see Saan PRD Writing; its output is the preferred input here, but it is not a dependency. To explain a business structure or process, see Saan Diagram or Saan Mermaid.

The prototype aligns interactions, states, and rules. It is not production front-end code, a visual design, or a mobile device mockup.

Get started

Install just Saan Prototype from Saan Kits:

npx skills add yishan/saankits --skill saan-prototype

Give your agent the specification:

Use saan-prototype to build a review prototype from prd.md. List the pages, roles, and scenarios first.

Needs Python 3 (standard library only) to build and check, and a browser to open the result.
