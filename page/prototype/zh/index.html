Saan Prototype

v0.1.0

把需求规格变成可交互的评审原型，在开发之前让大家先点一遍。

把带编号的规则、验收场景和待确认事项交给它，它会生成一个离线的 HTML 文件：切换角色和场景，试一试成功和失败时的反馈，看清哪些文案还是建议、哪些问题还没定。

适合
评审页面、角色、状态和规则
产出
单个 HTML 文件、可修改的源码，以及与规格对应的追溯表
准备
最好是一份 PRD；只有一段描述也可以，会先列出假设

试一试内置示例

一份虚构的设备借用规格，两个角色、三个场景。用顶部的评审栏切换场景、角色、主题和标注。

示例数据为虚构。单独打开示例。

从需求规格到评审文件

读取的内容

  1. 功能和页面：每个界面提供什么、从哪里进入
  2. 角色：谁能看到什么、能做什么
  3. 功能约束：前置条件、状态变化和失败反馈
  4. 验收场景：评审时应该能演示的情况
  5. 待确认事项和建议文案，原样保留

写出的文件

  1. prototype.html：内联了运行时、主题和页面的单个文件
  2. rules.js：每条已确认规则一个小函数
  3. scenarios.json：每个场景的验收编号、角色、当前时间和数据
  4. pages/*.js：页面，用列表、详情、表单、对话框、状态和时间轴范式搭建
  5. trace.md：页面、场景与来源编号的对应关系，以及没有画进原型的待确认事项和原因

动手前先给出范围，例如“4 个页面、2 个角色、9 个场景”，可以先删减再生成。

把一条规则变成评审时能点的操作

取自验证运行 · 会议室预约冲突

“占用区间为 [开始, 结束)。同一会议室的两个有效预约区间有交集即冲突；首尾相接（如 09:00—10:00 与 10:00—11:00）不冲突。”
  1. 规则：FR-C04 写成一个函数，预约对话框调用它并显示结果。
  2. 场景：“乙在甲的周会前后及另一会议室预约”对应 AC-02、AC-03、AC-04，初始数据里已有甲 09:00—10:00 的周会。
  3. 试一试：同一会议室 10:00—11:00 预约成功；09:30—10:30 被拒，甲的预约不变；另一会议室 09:00—10:00 预约成功。
  4. 待定：冲突提示文案未定稿（Q-12），文案带〔建议〕角标，点开能看到问题原文。

并发提交（FR-C05）无法靠点击演示，追溯表写明原型只演示可见的一半。

评审时可以做什么

  • 选一个场景。每个场景写明对应的验收编号，带着自己的数据和当前时间，因为“已开始”这类规则靠时间判断。
  • 切换角色，对比不同的人在同一页面能看到什么、能做什么。
  • 打开标注，看到建议文案、显示为占位块的待确认事项，以及每个控件背后的规则编号。关掉后是干净的演示版。
  • 在中性灰、品牌蓝和暗色三套主题之间切换，每套都通过对比度检查。

只做规格确认过的内容

  • 已确认的规则写成小函数，页面的反馈都由它们决定。
  • 待确认事项不会被猜成一个答案。它显示为占位块，或者在追溯表里写明为什么不涉及。
  • 不加规格之外的页面、步骤或状态。只为串联页面而加的元素标为建议。
  • 检查器把每个标注和场景追溯到来源编号，拒绝新增状态和外部请求，并列出没有被任何场景覆盖的验收场景。

两个案例各在全新上下文中跑了两轮，评审标准在生成前写定：room-booking 的 PRD（24 个验收场景），以及一段只有三条规则、没有 PRD 的描述。四次都符合标准。评审中发现的运行时和说明问题，已在两轮之间修改。

检查只核对编号和文本，不评价交互是否好用；原型也没有做过真实用户测试。

什么时候用这个技能，什么时候用别的

评审前，需要大家实际点一遍页面、角色和状态，而不只是读文档时使用。写需求本身，见 Saan PRD Writing；它的产出是这里的首选输入，但不是前提。讲清业务结构和流程，见 Saan Diagram 或 Saan Mermaid。

原型用来对齐交互、状态和规则，不是可上线的前端代码，也不是视觉稿或移动端设备外框。

开始使用

从 Saan Kits 中只安装 Saan Prototype：

npx skills add yishan/saankits --skill saan-prototype

把规格交给 Agent：

用 saan-prototype 根据 prd.md 做一个评审原型。先给我页面、角色和场景清单。

打包和检查需要 Python 3（只用标准库），打开原型需要一个浏览器。
