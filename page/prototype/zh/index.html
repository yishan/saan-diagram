Saan Prototype

v0.2.0

开发前，把需求里的关键操作做成原型，让团队先试一遍。

打开原型，换一个角色或场景，就能看到谁可以操作、点下去后状态怎么变、失败时界面怎么提示。还没定的规则和文案会标在相关位置，评审时可以直接指着页面讨论。

适合用在
开发前评审，核对页面操作和业务规则
得到什么
可离线打开的 HTML 文件、可修改的源码和需求对照表
准备材料
优先用需求文档（PRD）。也可以从功能描述或截图开始

试着借一台投影仪

选「投影仪可借」，点「借用」，看设备状态变成「已借出」。再换到「投影仪已被乙借出」，试试同一个按钮会给出什么提示。打开标注，可以看到借用期限和超期处理还没定。

准备材料与交付文件

先确定评审范围

从需求材料里整理页面入口、角色权限、操作条件和验收场景。生成前会列出这次要看的页面、角色和场景，方便你删减。只有简短描述或截图时，会先写明假设，并把界面文案标为建议。

评审后还能接着改

  • 用浏览器直接打开 prototype.html，一个文件就能带到评审会。
  • 页面、规则和场景的源文件会一并保留，修改后可以重新生成 HTML。
  • 用需求对照表 trace.md 查到页面和场景对应的需求编号，也能看到哪些待确认事项没有放进原型，以及原因。

同一条预约规则，怎么在原型里试

会议室预约 · 验证案例

规则 FR-C04 规定，同一间会议室的有效预约不能有重叠。下一场从上一场结束的时间开始，可以正常预约。

评审场景里，甲已预约 A 会议室 09:00–10:00 开周会。以乙的身份试下面三种预约，分别对应 AC-02、AC-03 和 AC-04。

  1. A 会议室 10:00–11:00。与上一场首尾相接，预约成功。
  2. A 会议室 09:30–10:30。与周会重叠，预约被拒，甲的预约不变。
  3. B 会议室 09:00–10:00。时段相同，但会议室不同，预约成功。

冲突提示还没定稿，界面标为「建议」，点开标注可以看到待确认事项 Q-12。

两个人同时提交时，系统如何保证只接受一笔预约（FR-C05），需要在有并发处理的系统中验证。

评审时可以做什么

  • 切换场景会重置数据，并切到该场景设定的时间。这样可以反复试同一笔预约在开始前后能否取消。
  • 切换角色，对比不同的人在同一页面能看到什么、能做什么。
  • 打开标注，查看建议文案、待确认事项和操作对应的规则编号。关闭标注后，可以专心走一遍操作流程。
  • 按演示需要切换中性灰、品牌蓝或深色主题。

交给团队前会检查什么

原型按已确认的规则模拟操作。待定内容会在相关位置标出，或在需求对照表里说明为何没有展示。为串起页面而补充的入口也会标为建议。

自动检查会找出对不上的需求编号、未演示的验收场景，以及页面代码中的外部资源请求。操作结果还要在浏览器里逐个场景核对。

仓库保留了会议室预约和简短功能描述两组验证案例。两组各试做两次，均达到事先写明的评审标准。后续修正做了自动检查和浏览器复查。真实用户测试尚未开展。

怎样和其他技能配合

需求还需要整理时，可以先用 Saan PRD Writing 写清规则和验收场景，再用原型演示这些操作。评审时如果需要看系统之间的关系，或一项业务怎样在不同岗位间交接，可以用 Saan Diagram 或 Saan Mermaid 补一张图。

开始使用

单独安装 Saan Prototype。

npx skills add yishan/saankits --skill saan-prototype

安装后，把需求文档交给你使用的 AI 助手。

用 saan-prototype 根据 prd.md 做一个评审原型。先列出要演示的页面、角色和场景，再把待确认事项标在相关界面上。

生成和检查原型需要 Python 3，无需额外安装 Python 库。评审者用浏览器打开 HTML 文件即可。
