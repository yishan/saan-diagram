# 流程路径验证（verify）

> 用 `python3 scripts/render.py --guide verify` 输出本文。

流程图、泳道图、审计流程图画的其实是一个**业务声明**："付款前必须经过三单一致""审批和执行不是同一个人"。`verify` 把这些声明交给脚本，对图上的流程做可达性与控制点绕过检查，而不是靠人看。几十毫秒，不用装任何东西。

只支持阶段类图示（架构视图 / 主流程 / 泳道 / 审计流程图）。默认步骤集合包含 module、hub、decision、optional、special（含旧名 ai）节点，即使没有连线也检查；系统、单据、存储和路径行标题不算步骤。参与验证的是 `kind: flow`、`kind: return` 和自动生成的相邻路径步骤连线；显式 data 连线不算流程。

若混合图只验证部分流程，可用 `verify.nodes: [节点引用, ...]` 明确范围，并说明排除原因。不能为了隐藏不可达步骤而缩小范围。推断起终点时不把完全孤立的节点当作合法起终点；多入口或指定结束状态应显式写 start/end。

## 写法

```yaml
verify:
  start: 提交付款申请          # 可省略：默认是没有流入（不算 return）的步骤
  end: [执行支付]               # 可省略：默认是没有流出的步骤
  must_pass:                    # 控制点不可绕过
    - {before: 执行支付, through: [核对合同验收, 审核发票, match]}
  separate:                     # 岗位分离：比较明确声明的 actor 或角色列
    - [提交付款申请, 执行支付]
  # 以下默认开启，写 false 可关掉
  reachable: true               # P2：每一步都能从起点走到
  terminates: true              # P3：每一步都能走到终点
```

引用节点用 label 或 id；`paths` 里的步骤用 `<行名>.<id 或 label>`。

## 规则（都属于业务发现类）

| 编号 | 查什么 | 失败时输出 |
|---|---|---|
| **P1** | `must_pass`：从起点到 `before` 的每一条路径都经过 `through` 里的每一步 | 被绕过的控制点 + 一条反例路径，如"提交付款申请 → 紧急付款审批 → 执行支付" |
| **P2** | 每一步都能从起点到达 | 走不到的步骤 |
| **P3** | 每一步都能走到某个终点（没有死路，也没有出不去的回路） | 从起点到死路的路径 |
| **P4** | 每个判断至少有两个出口 | 只有一个出口的判断 |
| **P5** | `separate` 里的两步的声明角色不同，且角色信息完整 | 共同角色，或角色待确认 |

通过的检查会写在图例下方，例如"已验证：到达『执行支付』之前必经『核对合同验收』『审核发票』『三单一致？』"。这一行是给读图人的信任信号，比"我们有控制点"更有说服力。

## 发现问题时

**不要为了通过而改图**：删掉那条绕过的连线、把节点挪到别的列，等于把流程漏洞藏起来。正确做法：

1. 把反例路径原样告诉用户，问"这条路径现实中存在吗？"；
2. 不存在 → 是图画错了，按用户说的改；
3. 存在 → 这是真实的风险。用户确认后写进 `accept`，图例下方会写明"已确认的发现"和说明：

```yaml
accept:
  - {code: P1, match: 紧急付款审批, note: 紧急付款经总经理书面特批，事后补审}
```

## 什么时候值得写 verify

- **审计流程图**：几乎总该写 `must_pass`，控制点能被绕过就等于没有；
- **审批流 / 泳道图**：写 `separate`，检查不相容岗位（申请与审批、经办与复核、记账与出纳）；
- **主流程**：写空的 `verify: {}` 就能检查死路和单出口判断。

路径验证解决的是"会不会走错路"。如果担心的是"同时发生会不会出事"（审批中途撤回、两个子公司同时改同一个供应商、超时自动通过与人工审批的竞态），那是并发问题，需要 TLA+ 之类的模型检查，超出本 skill 的范围，应向用户说明。

## 角色身份与排版分离

优先在步骤上声明 `actor`。只有材料明确表明列代表角色时，才写顶层 `column_semantics: roles`；此时缺少节点 actor 的步骤使用列的 actor、label 或 id。相同 actor 即使分在不同列也违反岗位分离；不同 actor 可以排在同一列。信息缺失返回 P5 待确认，不会输出已验证。

```yaml
nodes:
  - {id: apply, label: 提交申请, col: pre, actor: 申请人}
  - {id: pay, label: 执行支付, col: post, actor: 出纳}
verify:
  separate: [[apply, pay]]
```

这只验证 spec 声明的角色差异，不证明人员身份、账号授权或生产系统实际执行了岗位隔离。`verify: false` 或省略该字段关闭检查；`verify: {}` 与 `verify: true` 开启默认检查。
