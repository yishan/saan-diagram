# Saan Diagram（saan-diagram）

> 作者：Yishan · 版本 v1.0

把业务描述、需求文档、白板截图转成**统一规范的业务图示**。模型只写 YAML spec（用阶段 / 泳道 / 行定位，不写像素和颜色），坐标、走线、配色、图例都由 `render.py` 计算，校验不通过不能交付。

**核心原则：统一的是约束语言，不是具体方案。**

本文只放每次都要用的内容。某类图的详细写法用 `python3 render.py --guide <主题>` 按需读取，不要一次读全。

---

## 0. 选图示类型

**先问一句：一段文字或一张三列表格能说清吗？** 能，就不画。

| 你要表达的是 | 图示 | 起步模板 `--init` | 详细写法 `--guide` |
|---|---|---|---|
| 各阶段有哪些模块，接哪些系统 | 架构视图 | `arch` | `stages` |
| 一条主流程，含判断和回退 | 主流程视图 | `flow` | `stages` |
| 几种方式各走过哪些阶段 | 路径对比视图 | `paths` | `stages` |
| 多个角色之间的交接 | 泳道图 | `swim` | `stages` |
| 数据从哪来、经过哪些处理、存到哪 | 数据流图 | `dfd` | `profile` |
| 单据与关键控制点（内控、审计） | 审计流程图 | `audit` | `profile` + `verify` |
| 哪些环节不增值 | 机会流程图 | `opportunity` | `profile` |
| 平台由哪些层组成、对外接什么 | 分层架构图 | `layers` | `layers` |
| 业务对象及其关系、几对几 | 实体关系图 | `er` | `er` |
| 谁管谁，谁能看到谁的数据 | 组织架构图 + 数据隔离 | `org` | `org` |
| 一个结果背后有哪些原因 | 鱼骨图 | `fishbone` | `fishbone` |
| 关键节点什么时候到、偏了多少 | 里程碑时间线 | `timeline` | `timeline` |
| 两个维度上该先做哪个 | 四象限图 | `quadrant` | `quadrant` |
| 每个活动受什么约束、靠谁完成 | IDEF0 功能模型 | `idef0` | `idef0` |
| 时序交互、状态流转、物理表结构、甘特图 | **不用本 skill** | — | 用 Mermaid 或数据库建模工具 |

两种都想用时挑主轴：阶段是主轴用架构视图，步骤先后是主轴用主流程，角色交接是主轴用泳道图，技术分层是主轴用分层架构图。泳道、路径视图、重点能力（浅橙色）都不是必备的，材料里有才画。

## 1. 动笔前：一次问完

**请求里已经说清图示类型和交付方式时，直接画，不弹提问。** 否则用 AskUserQuestion 一次问完（最多 4 题），只问没说清的：

| 题目 | 选项 | 写进 spec |
|---|---|---|
| 类型 | 按 §0 给 2–4 种，推荐项放第一并标"(推荐)"，附上你从材料里看到的依据 | `layout` |
| 方向 | 横向（宽屏、PPT）／竖向（文档、手机、长流程）。只有阶段类图示问 | `orientation` |
| 配色 | 默认飞书蓝 + 线框标题栏／我的 VI 主色（在"其他"里填 `#RRGGBB`）／VI 主色 + 主色标题栏 | `brand` `titlebar` |
| 交付 | HTML + PNG（直接看图，不写外部系统）／飞书画板（可编辑）／两者都要 | 不进 spec |

- 题数超过 4 时，配色取默认，在"类型"题说明里写"要用 VI 主色请在'其他'里写色值"。交付方式不能省。
- 问之前用 `python3 wb_publish.py --probe` 探测一次（结果缓存 12 小时，不联网写任何东西），把结论写进"飞书画板"选项说明，如"已检测到 lark-cli 并已登录"或"未安装 lark-cli，选它需要先安装并登录"。
- 可选元素（核心底色、业务域方框、重点能力、范围标注等）不单独问：材料里明确出现的才开，交付说明里写明开了哪些。
- 用户不在场时取默认值：§0 推荐类型、横向、默认配色、交付 HTML + PNG（无人确认时不写外部系统），并在交付说明第一行写明。

## 2. 工作流

```bash
python3 render.py --init audit > pay.yaml        # ① 从最接近的模板起步，改内容，不从零写
python3 render.py --guide stages                 # ② 只在拿不准写法时读对应主题
python3 render.py pay.yaml --all                 # ③ 校验 + 路径验证 + HTML + PNG + 画板 DSL，一条命令
```

1. **抽取**材料里的阶段、主线步骤、模块、内外部系统、连线、判断、核心业务；材料是图片就逐项读出来。
2. **起步**：`--init <模板>` 输出一份能通过校验的完整示例，在它上面改。
3. **删减**：能删的节点、连线、框、底色都删（最好的改进通常是删除）。
4. **出图**：`--all`。失败时每条问题后面都附了修法，按修法改 spec 再跑。
5. **看一眼 PNG**（Read 打开）：校验查不出"看着别扭"。这一步不省。
6. **交付**：按 §5。

## 3. 几条不能破的规矩

- **颜色只留给"系统"和"核心"**：业务节点一律中性灰；系统块用 VI 主色（内部实心、外部提亮）；核心底色全图 ≤3 处；浅橙色只给"重点能力"一类（`kind: special`，名称在 `special: {label: AI 能力}` 里声明），一张图只突出一类。
- **字不缩**：节点名 ≤10 字、连线标签 ≤8 字，放不下就精简措辞；中文最小 12px。
- **线是正交的**：不画斜线，不穿节点，不叠线，箭头前要有可见的线段。
- **标题栏默认白底线框**，不占颜色预算。
- **原图里的穿线、错色不要照搬**，交付说明里写"原图 X 处已按规则修正"。

完整的文字与配色规则：`--guide style`；全部校验规则与修法：`--guide lint`。

## 4. 两类校验：排版类可以改，业务发现不许改

`--all` 把问题分成两组输出：

- **排版问题**（线穿节点、标签重叠、字太长……）：改 spec 直到通过。
- **业务发现**（IDEF0 活动没有制度控制、数据只进不出、数据域交叉、四象限压线、控制点被绕过、岗位未分离……）：**不许为了通过而改图**。删一条绕过控制点的连线、把节点挪到别的列、编一个不存在的制度，都等于把问题藏起来。正确做法：
  1. 把发现原样告诉用户（脚本已经给出业务语言的描述和反例路径）；
  2. 是图画错了 → 按用户说的改；
  3. 现实就是如此 → 用户确认后写进 `accept`，图例下方会如实写出"已确认的发现"：

```yaml
accept:
  - {code: P1, match: 紧急付款审批, note: 紧急付款经总经理书面特批，事后补审}
```

**流程路径验证**：审计流程图、审批流、泳道图建议加 `verify`，脚本遍历所有路径，检查控制点不可绕过、岗位分离、没有死路。通过的检查会写在图例下方。写法见 `--guide verify`。

退出码：0 通过 · 1 有排版问题 · 2 只剩未确认的业务发现 · 3 spec 写错。

## 5. 交付

- **HTML + PNG**：`--all` 已生成 `<slug>.html`、`<slug>.png`（以及 `<slug>.wb.json`）。把 PNG 发给用户，并告诉用户 spec 在哪：以后改图就是改 spec；换方向或主色加 `--orient` / `--brand` 重跑即可。
- **飞书画板**：**只能通过 `wb_publish.py` 写入，不要直接拼 lark-cli 写入命令。** 安全规矩写在脚本里，绕开脚本就等于绕开规矩。先读 `--guide feishu`，然后照脚本的退出码行事：
  - **20**：脚本已导出现有画板截图并停下。空画板就加 `--mode append` 重跑；非空就问用户追加还是覆盖，**没有用户明确同意不得覆盖**；
  - **10**：lark-cli 的高风险确认门禁。把提示原样告诉用户，同意后用 `--pass` 追加它要求的参数；
  - **0**：已写入，Read 核验截图后再回复用户。
  - 用户没给目标画板或文档时，问用户；**不要自己新建文档**。
- **两者都要**：先发 PNG 给用户看，再走飞书。

交付前确认：校验 PASS；只看主线节点、核心底色和实线能说出业务主干；每个系统块都有连线；交付说明写明假设、默认值和已确认的发现。

## 附录：取得脚本

1. skill 目录下的 `scripts/`（解压完整 skill 包安装时就有）；
2. 会话绑定的 Project 里有 `claude/saan-diagram/render.py`、`claude/saan-diagram/wb_publish.py` 时，用 Projects 工具 `project_read` 读取，原样写入工作目录；
3. 都没有时，请用户上传 `saan-diagram.zip` 或对应脚本。不要凭记忆重写脚本：校验规则和写入的安全规矩都在脚本里，重写等于换了一套标准。

拿到后先跑 `python3 render.py --selftest`：示例全部通过、每条规则都能被故意改坏的样例触发，才说明脚本完整可用。`--help` 里没有 `--all` 就是旧版脚本，请用户更新。
